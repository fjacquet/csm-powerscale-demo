Before you start

One shared foundation (array prep and DR design), two install tracks — K3s with Helm (verified in this lab) and OpenShift with the CSM Operator — and one multi-namespace DR runbook that works on both. Do Part A, pick one track (B or C), then run Part D.

Use CSM 1.18.0 or later

Dell advisory DSA-2026-448 lists critical fixes in CSM 1.18.0; earlier releases are affected. Use the dellctl binary and Helm chart version that ship with CSM 1.18.

Kubernetes version is in the CSM 1.18 support matrix

CSM 1.18 supports Kubernetes 1.35 – 1.37 and Red Hat OpenShift 4.18 – 4.22. Your K3s v1.37.2 clusters run Kubernetes 1.37, which is in range. For the OpenShift track, both clusters must run the same supported OpenShift minor release. The matrix lists upstream Kubernetes rather than K3s by name, so also confirm your Ubuntu release under Host operating systems.

Single-node clusters

The chart defaults to controllerCount: 2. On a one-node cluster the second controller stays Pending. Step K5 sets it to 1 in your values files before you install.

With ignoreNamespaces: "false" the driver groups volumes by namespace (per StorageClass and RPO): one volume group directory, one RG pair and one SyncIQ policy per namespace. The policy exists only on the source array; ps2 holds the matching local target. Policy names follow <prefix>-<namespace>-<target IP/FQDN>-<rpo>.

03a

Choose the grouping

SettingGroupsFailover unitUse when
ignoreNamespaces: "false" (this guide)One RG per namespacePer namespace — move one app, or loop over all for a site failoverSeveral independent apps; you want to test or move them one at a time
ignoreNamespaces: "true"One RG for every volume of the StorageClassAll or nothingOne tightly coupled application stack spread over namespaces

Site failover = loop over every RG

repctl acts on one RG at a time. Failing over “the active cluster” means running the action for each namespace’s RG — Part D scripts this from a namespace → RG map. A namespace using two replication StorageClasses or two RPOs ends up with two RGs; keep one replication class per app namespace to keep the map simple.

03b

Rules that apply to both tracks

  • Distinct volumeGroupPrefix per source cluster — csi-pri on primary, csi-sec on secondary.
  • 63-character limit on <prefix>-<namespace>-<IP or FQDN>-<rpo>. With the values here, namespace names can be at most 28 characters; a SmartConnect FQDN instead of an IP leaves less room.
  • IsiPath must be identical on source and target (/ifs/data/csi).
  • Failover does not stop writes on the source on PowerScale — the runbook scales workloads to 0 first.
  • No CSI snapshots of SyncIQ-replicated volumes; protect them with array-side snapshots or backup tools.
  • Applications are not replicated. CSM moves volumes (data, PV and RG objects); Deployments, Services, ConfigMaps, Secrets, Ingress/Routes and DNS are your job (D2).

03d

Retention: what deleting on the source does to the replica

The replication StorageClass can carry remotePVRetentionPolicy and remoteRGRetentionPolicy (Delete or Retain). With Delete, removing a PVC or a whole namespace on primary also removes the replica on secondary — an operator mistake then propagates to the DR site. Use Retain for production DR and clean up deliberately. verify

What reprotect does on PowerScale

It deletes the CSM SyncIQ policy on ps1 and creates the reverse policy on ps2, so ps2 → ps1 replication protects the writes now happening on secondary. Until you reprotect (or fail back), changes on secondary are not replicated anywhere.
